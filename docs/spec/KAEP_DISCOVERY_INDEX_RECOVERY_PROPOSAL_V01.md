## 1. Outcome and current verified gap

**Required outcome:** an explicitly authorized *new* public Claude READ_ONLY KAEP source root can be persisted, its discoverable locator can be independently read and verified by the recipient, ambiguous partial commits can be recovered with the same stable source identity, and none of these facts is mistaken for actual authenticated model pickup, work authority, or full historical source coverage.

GitHub Issues provide two separately committed Issue-comment writes; they are **not atomic**. Existing `kaep_request_sender.send_request` saves the original and verifies its readback; `kaep_route_notice.route_request` independently verifies the original and submits a pointer to the public devflow #503 Issue. [PR #774](https://github.com/kinoko34077/devflow/pull/774) is an **OPEN, UNMERGED code-only pilot** of an opt-in two-phase receipt; its latest preflight can block before the first original post. It has **not** proven end-to-end delivery or acquired approval for live `--send`.

At the last bounded real #503 observation, there were **155 comments / 117 KAEP-prefixed markers**, including four owner-authored comments (`6256213272`, `6256292959`, `6258569300`, `6270176453`) with an extra single LF *after the closing fence*. Those bodies fail the **unchanged** canonical `decode_comment` (`INVALID_WRAPPER`). JSON validity after manual trimming is **not** wire validity, nor a basis to trust or replay the entries. No historical comments are changed here. There is also a **different, source-side** malformed historic comment at kinotch-repo-monitor #81, `6244325853`, blocking B5 source-universe parity; fixing the index would not fix that original.

### Crucial implementation distinction

- **Index reader (already accepted A3):** `kaep_discovery_reader.discover_batch` rejects an invalid individual index comment, records its ID/reason, and can continue independently valid pointers, while pinning durable cursor on an unreadable **original**. Tests already cover malformed index markers (`tests/test_kaep_discovery_reader.py::test_malformed_marker_cannot_hide_later_valid_pointer`) and source-blocked cursors. This does **not** mean complete coverage or permission to act.
- **Index writer (currently blocked):** `kaep_route_notice.route_request` calls the generic `kaep_request_sender.send_request`, which reads the **entire** #503 history through shared strict `_mailbox → read_mailbox`. One malformed KAEP-prefixed comment raises `INVALID_WRAPPER`, preventing normal append. Broadening `decode_comment` to accept new trailing text or silently mutating history would change an established security/provenance boundary.
- **Original-to-recipient reality:** historical devflow #726 had three Claude READ_ONLY source roots without valid #503 locator matches, *but all three have correlated ACK+ANSWER comments*. Missing an index pointer is an actual **registration/observability gap**, **not** proof of lost Claude work or a pending task. Model/session origin remains separately unverified.

## 2. Recovery candidates (shared evaluation axes)

| Candidate | Existing original/index preservation | New public resource/consumer migration | Security proof needed | Main limitation |
| --- | --- | --- | --- | --- |
| **A. Index-local pinned quarantine (limited pilot)**: isolate only an explicitly owner-reviewed finite set of exact legacy malformed comment bytes for append-admission; reuse strict decoder on *all remaining* entries and deny-only collision inspection of quarantined bytes | Unmodified source and #503 Issue; never promote quarantined entries to valid messages | None if genuinely local | Exact GitHub actor + comment ID + immutable SHA-256 of full body; changes fail closed; byte-identical review evidence; deny if uncertain id/key collision, extra unknown marker, incomplete page or body mutation; independent security review | Adds per-entry exception risk, possible time-of-check/time-of-use race; index can remain `PARTIAL_UNKNOWN`; not a full source registry |
| **B. Versioned successor index with backward-compatible dual-read**: append *new* source locators to an independently designated clean public owner Issue; preserve old #503 as historical read-only; consumers merge strict-validated original-root identities | Original and old #503 bytes unchanged | **Yes** — an explicit owner-approved public Issue, new index contract, rollout/dual-read tests | Independent security/visibility/actor/replay review; stable producer→pointer recovery; strict read-back and privacy gates; dedup same source tuple across old/new; migration parity and rollback | More implementation and public-surface changes; historical completeness not automatically solved |
| **C. Edit historic comments or globally accept trailing whitespace** | No, changes existing provenance or canonical wire grammar | None | Would require an explicit exception to strict v0.2 source authority | **Excluded under current accepted B5/#503 security conditions** |

**User decision:** B selected and the single public successor index [#789](https://github.com/kinoko34077/devflow/issues/789) created (empty, inactive); option A remains an unaccepted alternative. The creation permission **does not** authorize a new model-addressed REQUEST, broad source backfill, or unreviewed activation. ### B read-only compatibility pilot (not a migration)

An **opt-in in-memory test helper** `tools.kaep_discovery_reader.discover_dual_index_shadow` reuses the accepted A3 strict `discover_index_shadow` source verifier **twice**, one for the existing #503 index and one for a synthetic successor Issue (test fixture number only; no actual GitHub Issue is created). The optional `index_issue` argument defaults to #503 and does not change the existing CLI/default reader. Both readers retain exact `task_ref`, Github actor, pagination, KAEP v0.2 wire format, original Issue verification and per-index rejection/blocked cursors. Neither can recursively treat either known index Issue as an original source.

Dedup is only allowed for the **same strictly original-verified tuple** `(owning_issue, source_message_id, source_comment_id)`; cross-index identity conflicts or a rejected/blocked/truncated index produce `PARTIAL_UNKNOWN`, not a queue, merged cursor, permission, or full-source proof. For a clear bounded fixture, `BOUNDED_DUAL_INDEX_READ` remains **bounded only** with `has_unknown_work=true`; authenticated agent pickup remains false even with two identical pointers.

Admission tests intentionally include: duplicate verified old/new pointer; malformed old index with valid later pointer (no starvation, still partial); untrusted new actor; successor/legacy loop; corrupt original source; incomplete batch and provider failure; invalid successor Issue. This pilot is **not enabled in the default check-in flow** and cannot publish an index or issue. An actual successor index needs separate #503 owner authorization, security review, privacy/transport proof, and then live recipient session E2E.

### B producer-to-A3 offline pointer compatibility pilot (not publication)

`tools.kaep_route_notice.route_request` (the accepted existing pointer composer) now accepts optional `discovery_issue`, default **unchanged #503**. Any non-#503 target is admitted **only with both explicit offline GitHub-page fixtures and `do_send=False`**. It uses the same `verify_source_request` and `kaep_request_sender.send_request` with target-specific `task_ref` and idempotency identity. A successor target with `--send` always fails **before any GitHub read or write** with `SUCCESSOR_INDEX_NOT_APPROVED`; the CLI does not publish or create an index. A self-loop or invalid target fails before composing a message.

An offline regression prepares one valid original, captures the existing route composer's successor-target pointer payload, constructs its exact existing KAEP v0.2 envelope through `make_request`, and feeds it to `discover_batch(index_issue=synthetic_successor)` for independent strict original/recipient readback. Invalid/partial fixture and forbidden live publish scenarios are negative-tested. This proves **serializer/parser compatibility in fixtures**, not public-index selection, real POST/readback, recipient model pickup, migration authorization, completeness, or source visibility. Production successor routing requires explicit #503 owner decision, independent security validation and a separate code change to remove the intentional non-#503 send lock after approval.

### Approved #789 producer admission contract (S2 code-only; live REQUEST not sent)

The existing `tools.kaep_route_notice.route_request` retains its historical **default #503** and accepts **explicit** `--discovery-issue 789` for the only user-approved public successor Issue. Every *other* target remains denied for live `--send` (synthetic targets are usable only with offline fixtures); either #503 or #789 cannot be used as an original. The existing strict source verification and `send_request` pointer writer are reused, not forked.

The existing `tools.kaep_send_with_discovery` two-stage producer also retains default #503 and optionally accepts exactly `--discovery-issue 789`. A shared strict target-index GET/_mailbox preflight now checks the **selected** destination before any original source POST. Thus the historical malformed #503 blocks legacy target, but its corruption does **not** block a clean #789; if #789 later becomes malformed or its GET is unavailable, the original is not posted. `--send` remains explicit and requires a public source repo; route_request re-checks public source visibility before posting the pointer.

This staged implementation grants **no** automatic task dispatch, auto-ACK/ANSWER, other Issue write destination or private source publication. No new REQUEST or pointer comment is posted during the code/test PR. Tests must verify: positive mock #789 POST/readback; clean #789 preflight (without reading corrupt #503); #789 malformed/transport failure prevents original writes; invalid arbitrary destination and loop denied before any remote write; legacy default and preflight preserved; real model pickup remains unproven. The user authorized the new public index, not an arbitrary new KAEP task.
## 3. Proposed phased acceptance, independent evidence and rollback

1. **R2.1 — Source evidence + authority.** Re-read live `#503` and owning Issue at the exact test time; record total/pagination, every rejected marker ID, raw-body digest metadata (no request prose in reports), actor and edit/time provenance. Confirm old pointer and original identities under canonical validators; distinguish a GitHub transport account from an authenticated worker identity. Pick A or B *explicitly at #503*, recording why the other's risk is unacceptable.
2. **R2.2 — Read-only compatibility pilot (no new Issue/write).** Reuse `kaep_discovery_reader` and B6 strict original reader; prove in offline positive/negative tests that healthy index pointers still surface despite a malformed index item; malformed original and pagination/provider corruption never become verified roots. For B, simulate two strict index histories and dedup by `(owning_issue, source_comment_id, source_message_id)` only after verifying originals, not by issue title or an untrusted candidate list.
3. **R2.3 — Producer contract only (code and tests first).** Reuse `send_request`, `verify_source_request`, `route_request` and established actor/visibility parsers. Make all target/source/private checks **before** first POST; a source-only commit must return an explicit partial receipt, a lost original readback must not trigger speculative locator publication, retries reuse the same `request_key`; force conflict/unknown on collisions. If choosing B, make the target index an explicit injected/validated capability rather than duplicating source/codec implementation.
4. **R2.4 — Security/human gates.** New public Issue, public locator write, private-source visibility exception, old-index exception, credential or permission changes, schema/cursor cutover and unattended producer rollout need their respective explicit authorization and a **truly independent current-HEAD review**. A same-system COMMENT, Codex automated summary or shared-GitHub-login claim is not automatically independently authenticated provenance. Required CI and Review readiness must be verified on that exact head.
5. **R3 — New real request acceptance.** On a genuinely needed and authorized new public READ_ONLY request only: (a) exact root POST/readback; (b) locator registered/read back in accepted index; (c) an actually running authorized recipient independently reads and validates the original/recipient/expected HEAD; (d) a correlated ACK/ANSWER appears, without inventing worker session identity, prior ACKs or model wake. Check partial crash/retry traces and record explicit time/cursor boundaries.
6. **R4 — Rollback and legacy retirement.** Dual-read can roll back to old read-only #503/Control without deleting original receipts; **never** retire fallback while any original-source universe is `INCOMPLETE`, while historic B5 source is blocked or while receiver-session and privacy claims are unproven. Do not mark broad B5 or B6 accepted just because a new index exists.

## 4. Required adversarial test cases before any real publish

| Test input | Required behavior |
| --- | --- |
| Existing malformed legacy #503 marker; one later healthy pointer | Healthy pointer is independently verified by existing A3; malformed is rejected with ID/reason; never yields authorization or all-work completeness |
| Extra malformed marker not on any reviewed exception list | No writer admission; `BLOCKED` and original POST count 0 |
| Quarantined comment has same ID but changed body/author, or ambiguous unparsed key collision | No writer admission; no implicit trust, no silent skip; no original POST |
| Any GitHub index/source pagination gap, stale cursor, partial fetch or rate-limit | Return unknown/block; do not infer absence; no speculative new pointer |
| Duplicate exact source root / changed payload with same stable key | Reuse existing idempotent source and pointer when byte/actor matches; conflicting identity fails closed |
| Source public→private visibility flip between first check and pointer POST | Second public-visibility check blocks pointer; source-only result explicit; never leak private original location |
| Consumer sees duplicate old/new pointer to same original, or untrusted index author | At most one strictly original-verified root; reject untrusted pointer, no new task authority |
| Crash before source POST, after source POST, before pointer POST, after pointer POST but before readback | Every replay yields consistent proven/partial/unknown receipt using same key; never posts fresh identity on uncertain prior write |
| Receiving worker not running / only transport comment exists | `recipient_pickup_proven=false` until *independent actual session* evidence; ACK/ANSWER relation alone is transport correlation, not worker authentication |

## 5. Non-goals and decision boundary

No new database, client token, Cloudflare/D1 provider, live GitHub Issue publication, history mutation, legacy backfill, effectful worker wake, Claim, secret-containing text, or widening of known MIME/wire acceptance is authorized. Existing [B6 #680](https://github.com/kinoko34077/devflow/issues/680) index+recent-comment union is useful for **candidate discovery** but cannot prove an exhaustive original-Issue universe; do not accidentally promote it into a full registry.

**Decision gate:** the #503 protocol owner must explicitly accept A or B after the R2.1/R2.2 proof and review. Until then PR #774 remains OPEN/UNMERGED; its strict #503 GET-only preflight prevents predictable original-only partial writes and the manual Control fallback remains. This document is a design/acceptance proposal only.
